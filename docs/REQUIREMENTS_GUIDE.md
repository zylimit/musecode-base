# 需求指南（需求分析质量）

> 目标：需求从“形容词集合”变成“可执行、可回归、可追溯”的契约。本指南吸收 cc-base `04-requirements-and-design.md`（C7/C8），用 `scripts/check.sh` 做机器闸。
> 模板见 `docs/REQUIREMENTS_TEMPLATE.md`；变更记录见模板 §8 CHANGELOG 成对要求。

## 1. 四种来源标记（强制）

每条需求/规则必须带且仅带一种标记；没标的一律按 `[推断]` 对待：

| 标记 | 含义 | 下游用法 |
|---|---|---|
| `[确认]` | 用户确认的事实，注明来源（原话/案例编号/日期） | 实现者照做；反例出现时先摆矛盾再问 |
| `[推断]` | AI 的推断，注明推断依据 | 现场证据相反时报“需求存疑”+ 反例，不自行改需求 |
| `[默认]` | AI 采用的低风险默认，用户只行使否决权 | 照做；用户随时可否决 |
| `[待定]` | 没弄清的 | **只许出现在待定表**；功能条目挂 `[待定]` 即 fail（`PENDING_IN_REQUIREMENT`） |

机器闸（`check.sh`）：功能条目无标记 → `NO_SOURCE_MARK`；功能条目挂待定 → `PENDING_IN_REQUIREMENT`。

## 2. 交互四档（开口前先判档）

判据 = 不确定程度 × 做错代价：

| 档 | 场景 | 做法 |
|---|---|---|
| 直推 | 边界清、有依据、错了易改（改文案、加选项、换默认） | 不问，改完一句话复述 |
| 确认 | AI 能推断但会改变行为（“导出”是筛后还是全部） | 推断 + 推荐 + 最多 2 问 |
| 探索 | 为什么/谁受益/现状/例外任一不清且代价高 | 进“向人学业务”（§3） |
| 委托 | 用户说“你定/别问了” | AI 定，标“AI 决定（用户委托）”，不回头问 |

问法纪律：问过去的具体事（“上次怎么做的”），不问未来假设；查得到的事实自己查（代码/库/文档），不问人；听到“一般/通常/应该”标 `[推断]` 并要例子；听到“都要/越多越好”逼单选（“只能保一个保哪个”）；与前文矛盾时两句并排让人选，不自己圆。

## 3. 收敛条件（Spec 何时算够）

硬条件（`check.sh` 覆盖标 ★ 的）：

- [ ] ★ 待定表清零，或每条有“谁能答/押后到/不答先按什么做”（`PENDING_ROW_INCOMPLETE`）。
- [ ] ★ 功能条目无 `[待定]`、有来源标记。
- [ ] ★ 无占位符残留（`<...>`/TBD/待补字样，待定表内“待定”二字除外）（`PLACEHOLDER`）。
- [ ] 成功判据可数、技术无关、有基线、有反向指标。
- [ ] 矛盾清零；`[确认]` 有真实案例支撑。
- [ ] 复述通过（§4）。

软判据：交接测试（没参与对话的工程师能直接开工？）、边际测试（再问一题会改变做什么吗？）、不对称原则（缺了会返工的问到底，便宜能补的进待定表放行）。

## 4. 交付 = 复述通过（签字闸）

无“请批准”按钮。签字形式是复述：用用户给的案例讲一遍上线后那次会怎么发生（谁打开什么、看到什么、系统做什么、例外/失败各怎么走），每段结尾问一个具体的“那次是不是这样”。挑错 → 改对应条目并回“改了第 X 条”；挑不出 → 通过。

复述前先跑机器闸（机器能挑的错不拿给人挑）：

```bash
bash scripts/check.sh --req docs/REQ-<slug>.md
```

没过复述不进开发计划。

## 5. 迭代：CHANGELOG 成对 + 分类回退

改 Spec 必须追加 CHANGELOG（只改其一不算；三文件同步铁律）。一条记录回答：为什么改 / 原判断哪里错（第几条、当时依据）/ 影响 / 分类与回退。

| 变更影响 | 回退到 |
|---|---|
| 只改描述、无行为影响 | 不回退 |
| 改流程/界面/数据/权限/平台 | 设计（架构/DFX/Brief）→ 重排计划 |
| 设计不变、只改工作量 | 开发计划 |
| 代码缺陷、需求没错 | 修 bug，不改 Spec |

被推翻条目标“→ 被 \<日期\> 取代”，不删历史，不复用编号。

## 6. 需求存疑回流（下游→需求）

审查/测试/修复/排计划发现“代码对得上 Spec、Spec 对不上业务”时不停工猜测，按统一格式回流：**情境 → 按 Spec 会怎样 → 业务上应怎样 → 依据**。主 Agent 走迭代模式（§5）更新 Spec + CHANGELOG + 复述，再按分类回退派工。下游四者都不替需求改 Spec。

## 7. 上下游输入关系（防断链）

- Spec → 架构/DFX：数据归属与权限、故障后果、隐含合规、涉钱涉人身条目。
- Spec → 开发计划：核心价值排序、成功判据、`[推断]/[默认]/[待定]` 清单（计划先验证假设）。
- Spec → 派单：每条功能的“为什么、谁受益、规则与例外”是派单包 Business Context 的来源。
- DFX → 架构：质量场景是架构驱动因子；缺则在决策处标 `[待 DFX 补充]`。
- 架构关键决策、DFX 档位与优先级栈即时进 `progress.md` Decisions；“既定不可碰”进 Pinned。
