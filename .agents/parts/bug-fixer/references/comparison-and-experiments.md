# 正常对照与诊断实验

故障有多个解释、只在部分环境出现，或“修过仍失败”时读取。目标是找到能改变判断的证据，沿原 Skill 的红测锁与三次熔断执行；不新增固定假设数量或重试轮次。

## 先找可比的正常路径

保留原始异常输入、时序、权限、版本和实际结果，再找最近一次正常记录或相似的正常路径。比较双方哪些条件相同、哪些不同；不同账号或不同对象的成功不能直接排除权限、状态与数据差异。

沿输入解析、领域判断、状态写入和输出边界逐步对齐同一含义，找**第一次可观察分歧**。分歧位置帮助圈定调查，不必然就是根因：上游给错单位可能直到渲染才显现。没有正常样本时可从已确认契约构造最小对照，并明确它是合成对照，不伪称曾在生产正常。

选择观测点时只取诊断所需的脱敏字段。时序问题保留事件先后与对象/请求关系；敏感日志、完整业务数据和凭据不是默认输入。

## 用一个实验区分解释

对仍成立的候选原因，用已有调查笔记写清：

| 候选解释 | 已有支持 | 哪个结果会反驳它 | 最小区分实验 | 实际观察及下一步 |
|---|---|---|---|---|
| 来自本次调用链的具体解释 | 能定位的输出或状态 | 可观察且与解释不相容的结果 | 尽量只改变一个相关条件，写预期差异 | 执行后填写；未执行保持未知 |

例如输出数值错误可能源于入口单位误解，也可能源于聚合重复。先保持同一对象和输入，对比进入聚合前后的值与次数；不同时改 fixture、格式化和缓存，使实验无法区分原因。固定期望来自业务规则；独立预期的细节见 [测试参考](../../test-builder/references/independent-oracles-and-evidence.md)。

阴性结果也要更新判断：某次变化未影响异常，只能排除实验实际覆盖的解释，不代表所有同类原因都已排除。环境不一致或观测没触达故障路径时，先修实验前提，不能把它算作产品通过。证据不足可以说“当前怀疑”，但必须带支持、反驳条件与下一步；不为显得确定提前宣布根因。

## 保住现场，再谈止损与修复

正在造成损失且已有紧急操作授权时，可以先做有范围的止损，保留可得现场并核验影响。止损、临时绕行与根因修复分别报告；不能因服务恢复就抹去未定位的原因。重启、清缓存、加 timeout 只有在对应假设和授权成立时才是实验或止损，单凭“慢”“CPU 为零”不能推定死锁。

准备修复的足够依据是：确认的规则、可复现差异、能解释关键观察的原因，以及能在修复前因该原因失败的锁。无法复现时交回已排除条件与具体缺口，不承诺已找到根因。保持锁的输入和断言；新增事实若证明测试口径错误，由主 Agent 校准依据后显式说明调整，不能为变绿削弱保护。

## 给复验者留下能重跑的判断

交接原始复现、正常对照、有效反证、最小修复、原锁及其结果，并标出哪些环境/并发路径没测。复验先确认原异常消失，再确认正常对照仍成立；现有 controls 与唯一 verification plan 继续决定必要范围。

若缺陷其实来自业务理解，返回最早失效的来源、具体例子与受影响 Task/验收，由主 Agent 更新后通知下游。需要时用 [字幕草稿案例](../../dev-builder/references/async-proofreading-case.md) 的“诊断与复验”观察如何区分返回成功与写入正确。
