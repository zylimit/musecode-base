# release-builder

- 版本：1.0.0
- 适用：构建→打包→发布→部署全链路。不适用：本地联调（dev-builder 内完成）。
- 输入：发布目标（打包还是发布/渠道/平台/版本）+ 项目构建约定。
- 输出：产物 + 隐私审计报告 + 部署验收三件套 + 回退预案。

## 步骤

1. 问清四要素再动手：打包还是发布、什么渠道、什么平台、版本号；区分本地 build/package/对外 release/deploy——授权覆盖实际动作，不从"交付"自动扩展。
2. 前置闸：相关功能回归测试跑过且通过（真实输出），复用 test-builder 套件；"部署/打包"指令不豁免此闸。
3. 构建打包：用仓库已有命令；先核脚本是否隐含安装/上传/环境写入；卡住先诊断（CPU 0% 且时长涨=死锁；配置声明≠实际状态，先验实际布局）。
4. 隐私审计（绝对底线，对**实际产物**执行）：开发者路径、*.db/.env*/credentials/密钥字样、私人数据目录；任一命中立刻停，修完重建。npm audit 无 critical。
5. 安装测试：从安装包测，不从构建输出目录测（dev 测通≠打包能用）；Desktop 装到系统目录、CLI 全局安装、Web 部署后在线测。
6. 部署验收三件套（主 Agent 独立核查，不信 deployer 自述）：容器创建时间+镜像 tag（勿看 Up 时长）、健康端点 200、live 冒烟（新功能产物真实存在）。
7. 发布 + 再验：用户确认后执行 tag/Release/publish/部署；发布后再验一次；失败先查"发生到哪里"（确认未发生/部分完成/未知三态，不把后一步失败写成前面全没发生），再走回退或前向修复（数据不可逆/已分发/版本不可复用时只能前向）；清临时产物，版本号文件已提交。

## 产物四环节（追查用户实际用的是哪个对象）

源树/构建 → 最终包（路径+digest+实际成员）→ 登记/安装副本（复制关系+解析目标）→ 加载实例（本次进程真实来源）。
禁推定：输出目录存在≠本次生成；清单合法≠归档完整；列表有名字≠用此次来源；登记成功≠旧会话已重载。
修正清单后必须重建产物再审计；旧 staging 与新包可能并存，不按文件名猜哪份可交付。

## 约束与红线

- 发布是有副作用的工作流：push/tag/publish/deploy 各自须有覆盖目标与动作的授权（`AGENTS.md` §5）。
- 密钥在平台配，不进代码；产物审计发现密钥即停，无豁免。
- 超时/断线/5xx 视为"可能已执行"，先查目标实况再定重试，不盲重远端命令。

## 验收

- 版本/CHANGELOG/工作区干净；构建零错误；隐私审计报告无命中。
- 部署三件套全过；回退预案已写明入口。

## 示例

CLI 发版：回归绿 → 构建 → 产物扫出 `.env` 残留 → 停，修 .gitignore+重建 → 全局安装逐命令冒烟 → 用户确认 → publish → 再验 `npm view` 版本与 digest。
