# 从记录到实际采用，及规则退役判断

反馈、项目进度与进化角色在“已写下教训”被当成“问题已经解决”、有重复问题或规则冲突、考虑减少规则时读取。各角色仍只写自己的授权路径；evolution-runner 只提出建议。本参考不新增统计阈值或自动毕业机制。

## 先分清改变了哪件事

从可定位的原事件开始，查当时已知的规则、用户新给的事实、AI 实际行为及造成的结果。按语义区分新业务规则、改变需求、合理共同完善、实现偏离已知规则，以及过早宣称完成；一句“还是不对”不足以单独判定归因。

一次事件可产生两项不同信息：项目规则由主 Agent 更新实际 Spec/设计并交 progress 保存决定与来源；AI 忽略已知规则的行为教训由 feedback-observer 记录。二者互指而不复制整段会话。重读、转述或多个角色引用同一事件不会使 occurrences 增加；只有有依据的新发生才计入。

## 每个阶段只声明它实际证明的事

以下是证据含义，不是新增状态字段，也不要求每次记录填满一张表：

| 已发生的事 | 可以怎样说明 | 仍不能说明 |
|---|---|---|
| 当前规则/教训已记入权威位置 | 已记录；给出位置、范围和替代关系 | 实现已改、已验证或用户满意。 |
| 具体代码/Skill/派单已修改 | 已落实到指定产物；给出当前改动 | 独立验收通过或后续角色已采用。 |
| 当前主体已有独立复验 | 在指定场景和环境下得到实际结论；保留失败与未验边界 | 所有场景有效、真实用户已认可。 |
| 下一角色据规则作出实际决定 | 引用它的产物/决策/复验，说明哪条规则改变了哪项行为 | 仅凭“已读”“会遵守”、角色 DONE 或沉默宣布习惯已形成。 |

progress 中的阶段性 Done 应明确完成对象和证据边界，未完成的整体工作保留 TODO/DOING 与下一 owner。Task 的最终完成仍由主 Agent 核对当前质量状态，不从作者措辞或笔记反推。没有给到某阶段证据就写尚未验证/待回填，不虚构历史发生过。

反馈写入后，当前任务立即采用已明确纠正；下一角色需要读到实际规则并改变对应 Task/验收。若权威来源已改、派单仍用旧解释，先让主 Agent 修正交接，而不是再记一条“用户反复改需求”。

## 按失效原因选择最小有效干预

先查现有规则和 Skill 是否已覆盖，再判断为什么没有发挥作用：

- **缺少或冲突的项目事实**：补正文、范围或替代关系；不将单项目口径毕业成通用规则。
- **已有来源没有进入派单或没被消费**：补必要摘录、补读入口及下游验收，观察下一角色实际使用；追加同义口号可能无效。
- **规则明确，缺少可执行判断**：在原规则或 Skill 补触发、区分例、答案分支、足够条件与交接，保留已做对的简明路径。
- **现有职责确实容纳不了重复操作**：说明为什么现 Skill 无法承接，再提新 Skill 或共享规则；不能只因 occurrences 高就扩大全局流程。

这是因果判断，不是“先补一句、再加一页”的固定顺序。候选写明具体失败、适用反例、最小位置、下一消费者和可证伪复验；正文更短、自动化更多、提问更少都不自动等于改进。样本、评分与候选阈值仍按 evolution-engine 正文计算，不用缺失证据填满统计。

## 退役先说明会失去什么

存在冲突、重复或维护负担时，可以提出合并/撤销建议，但先核对：

1. 原规则要防止哪个具体失败，影响哪些角色、入口、消费者与保护属性？
2. 失败条件是否真的不再存在？若由另一机制接管，替代覆盖在哪里，旧反例还能否被拒绝，正常路径是否仍可用？
3. 撤销后有什么残余风险和恢复办法，哪些验证尚缺？现有安全、秘密、权限、远端授权与保障底线不能由进化建议豁免。

没有命中、没有投诉、作者认为“模型已内化”，均不足以证明可删。提出的是可审查候选，正式变更按用户已有授权和当前保障要求由主 Agent 派发；没有授权就不实施。有授权也不把失败或 stale evidence 改为通过。

保留原观察、反证、拒绝原因及替代关系，不删除不合意的记录来提高评分。升级/退役完成后，用实际复验和消费者行为说明效果边界，再由授权记录者更新相关状态；不能因建议已接受就立刻声明毕业或恢复成功。

需要同一事件如何分流的示范时，读取 [字幕草稿案例](../../dev-builder/references/async-proofreading-case.md) 的“学习与后续采用”。案例是虚构教学，不计入项目 occurrences 或评分。
