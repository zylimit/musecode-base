# 独立预期与证据消费

测试双向转换、外部格式、状态链，或审查脚本/模型/浏览器报告时读取。本参考供 test-builder 与 code-review 共用；它解释怎样形成和判断证据，不新增 receipt 字段、质量状态或强制 E2E 清单。

## 先有单向预期，再判断往返

从当前有效规则取一个具体输入及固定预期。实现、导入端和导出端使用同一函数计算 expected，会让共同错误彼此印证；round-trip 返回原值，也可能是两端错误互相抵消。

按失效点选择必要检查：

1. **单向输出**：给定内部对象，直接按外部契约核对字段、单位、允许的格式和边界。不要用本次修改的导入函数解释输出后才作判断。
2. **单向输入**：使用独立确认的外部 fixture，直接核对内部结果。fixture 来源不能是本次待测导出函数；注明它支持的字段与版本。
3. **往返保留**：验证两端组合后是否丢失、重复、变义；分别检查调用方输入是否被修改。组合检查补充前两者，不替代外部契约。

虚构单位例：若项目已明确内部长度为毫米、外部为米，`2500 mm → 2.5 m` 和 `2.5 m → 2500 mm` 是两条单向期望。导出漏除、导入漏乘仍可能往返回到 2500。没有确认“小数位固定为两位”时，不能另要求字符串必须是 `"2.50"`；舍入、精度、非法输入等只采用实际来源。

选一个正常值和能区分目标错误的邻近/边界值，避免只测零值、恒等点或空集合。值的数量取决于要排除的故障，不为凑数量机械扩展。结构完整性应逐关键字段核对，数量相同不能证明每个对象正确。需要检查输入不变时，独立保存初始值并比较；一个已确认字段没变不证明整个输入无副作用。

**足够条件**：断言既能接受规定的正常行为，又能拒绝本次声称防住的具体错误，且 expected 有独立来源。若规则缺失，先保留可观测的实际结果，把缺失规则与受影响断言交主 Agent，不选择方便变绿的解释。

## 让 fixture 真的触达错误

沿生产入口核对 fixture 的身份、权限、状态和前置步骤。绕开校验直接调用内部函数可以测试局部逻辑，但不能据此声称真实用户路径成功。异步问题需要可控的事件次序；空等待或固定延时后没看到事件，不能等同于已执行并正确拒绝。

按规则/契约/集成/组件或 E2E 选择能暴露问题的最小层；错误只在重开或真实目标环境出现，就保留该边界的必要验证。低层通过不自动覆盖高层，某个目标通过也不替其他 required target 背书。范围仍由当前 controls 和 plan 决定。

## 读懂报告是怎样得出结论的

消费外部检查器或角色报告时，用下表解释其证据。只补本次判断所缺的部分，不为每份简短检查重新搭报告系统。

| 核对项 | 怎么判断 | 不足时怎样处理 |
|---|---|---|
| 对象与归属 | 具体源码/diff、产物、目标、运行或会话是否属于本次？与当前 subject/plan/policy 是否一致？ | 错对象、旧证据或会话歧义不能支持本次通过；定位正确对象或交回缺口。 |
| 环境与参数 | 实际版本、工作目录、fixture、strict/draft/可选开关和隔离设置是什么？ | 不把未开启、条件未满足或另一宿主的检查算进实际覆盖。只记录必要非敏感信息。 |
| 是否执行完成 | 应检查的样本/目标有多少，实际触达多少，进程是否结束，超时/取消/采集失败在哪里？ | 空集合、缺工具、超时无事件不是成功率 100% 或正确负例；保留未验证范围。 |
| 发现与判定 | 哪些 findings 进入 pass 条件？warning、采样、上限、过滤项怎样影响结论？ | 报告列出但判定未消费的问题仍需判断；截断不当作全量，启发式发现需按真实行为复核。 |
| 原始结果与协议 | 实际退出码、错误、报告路径和必要事件是什么？CLI、Hook 或异步任务如何表达阻断与完成？ | exit 0 可能仅表示脚本未作用于对象或成功输出 block；按实际协议解释，不只看末行。 |
| 能支持的业务结论 | 本次观察是否达到规则要求，哪些只是结构、模拟或局部运行？ | 结构合法、marker 清除、角色 DONE、列表可见均不能代替必要行为与 fresh receipt。 |

发现“有报告但无法确认跑过”时，先查本次运行与生成条件；不能从另一份文件的最新 mtime、自由文本中的工具名或静默结果猜执行归属。负例也必须有完成判断与可归属的观察；没有事件可能是采集失败，而不是路由正确。

## 放回既有信封与 finding

普通 Markdown 回传遵守所属角色契约：tester 使用 PASS / FAIL / BLOCKED / NEEDS_CONTEXT，reviewer 使用其既有工作状态。机器回执用本仓九段信封字段（Status/Changed/Verified/Not-verified/Needs-review-by/Evidence/Business-assumptions/Counter-examples/Domain-findings），状态只用四态、不新造 DONE 族 schema（供体原文为 `--output-schema .codex/harness/schemas/exec-envelope.schema.json` 的 DONE/DONE_WITH_CONCERNS，本仓无此机制）。不能把 Markdown 状态直接填进 JSON 键；两种载体都仍需当前主体的真实 receipt，Verified 不是质量批准。

review finding 的既有 `Basis` 说明独立规则，`Evidence` 写最小初态、操作、expected/actual 和实际运行或静态推导的区别，`Impact` 说明后果，`Fix` 给方向。录入 runtime 时映射到已有允许字段，不把教学表头作为新的 schema 键。未运行复验就明确未运行；审查发现了第一处问题也仍覆盖 controls 要求的后续 stage/lens。

跨阶段例见 [字幕草稿案例](../../dev-builder/references/async-proofreading-case.md)。先读取其唯一规则，再判断时序断言；不能凭实现里有版本号就认为它已被正确消费。
