# 按实际信息缺口设计 Skill

创建或丰富交互方法、编写复验场景时读取。以下是可选方法，不是每次执行必须完成的问卷。业务规则来自项目与人的经验；AI 负责查证、提炼、给出专业建议，并说明取舍和未知。

## 先明确下一步需要哪种判断

| 交互类型 | 适合的方法 | 可核对的产出 |
|---|---|---|
| 学习现行业务 | 从一件真实发生的事还原参与者、步骤、判断和例外；追问会改变解释的事实 | 当前流程与目标行为、关键术语、规则来源、一个反例 |
| 共同选择方案 | 用同一个任务比较候选；说明谁会受益或受损、代价与可逆性 | 推荐方案、取舍依据、尚未定的范围；用户委托可逆细节时直接采用建议 |
| 实现已有决定 | 先读实际来源和代表例子，核对输入/输出，再按既有模式推进 | 可体验的变化、验收依据、发现的规则冲突及受影响任务 |
| 诊断与审查 | 先查可得证据，用能区分假设的情境检验；把业务分歧与代码缺陷分开 | 触发条件、实际/预期差异、依据和影响，而非只列术语 |
| 学习与恢复 | 将纠正拆为业务事实和行为教训；更新当前来源，保留旧解释及替代关系 | 下一角色能使用的当前规则、来源和未决影响，不只是一条归档笔记 |

只选择能帮助当前判断的方法。例如修正文档中一个已明确的链接不需要行业访谈；工单“完成”的口径含糊则会影响状态、报表和测试，不能按惯例自行填入。

## 把维度名写成可执行的方法

“了解角色与流程”仍可能让 Agent 直接列一张表。正文应给出适用条件、动作、分支与收敛方式，例如：

1. 先用已给的一件业务实例，说明谁在何时做了什么，结果交给谁；没有实例时，主 Agent 只补会区分当前假设的事实。
2. 遇到“完成、有效、逾期”等词，查实际文档是否已有定义。用两个相邻情境检验边界，不要求每个常识词都重新确认。
3. 将建议写成可讨论的推导：“依据已知的验收规则，我建议把提交和验收分成两个状态，因为报表要区分它们。”如果规则未知，就保留待定口径，先做不依赖它的工作。
4. 用户纠正后，修改当前解释及其来源，指出哪些界面、Task 或断言需同步；下一阶段收到足够含义与实际来源，而非只收到“已确认”。

这类例子解释如何判断，不把某一项目的规则内置成所有任务的默认答案。子角色只向主 Agent 交回事实缺口，不直接与用户问答。

## 渐进披露时保留什么

- 主入口保留触发条件、必要前置、关键判断分支、继续/暂停条件和交接对象。
- 详细实例、不同领域的反例与试走方法放 references，写清何时需要读取。
- 模板承接已经形成的解释；不能把丰富的方法全部压成表头，也不能让参考文件只有路径却没有加载时机。
- 修改已有 Skill 时，先记录哪些能力已经有效、哪些有具体缺口，再做定向重写；篇幅长短不代表质量，不能为压行数删除承重例子。

## 一组用于设计的两轮示例

下面是合成情境，用于编写测试。执行对照时，只把当轮输入提供给被测角色，不提前给以下观察点或后续事实。

| 轮次 | 输入 | 观察什么 |
|---|---|---|
| 第一轮 | “我们需要看维修工单完成率。技师会提交处理结果，验收员之后验收。” | 是否区分已知流程与未知统计口径，先查已有定义；是否能说明口径会影响什么，并继续无关工作 |
| 第二轮 | “完成只算验收通过，退回的要重新处理；不要把技师提交也算进去。” | 是否立即采用明确规则，更新状态/报表/验收的解释与来源；是否还在重复追问已给口径或坚持第一轮猜测 |

同一输入在不同 Skill 下产物不同：需求阶段形成带来源的规则与例子；架构阶段解释状态与职责；执行/测试阶段需读到已确认口径再决定实现与断言。不把每一阶段都变成同样的访谈。

可以再选一个清楚的小改动，确认新 Skill 没有为明确任务强加访谈；或选“用户明确委托可逆细节”的例子，确认仍能给专业建议并推进。只选与本次修改有关的少量场景。

## 记录真实比较，承认验证边界

对照保留版本、输入顺序、可见依据、实际回应与产物。分别写原版做对了什么、改版做对了什么、回归和未知；不把未执行的设计场景写成结果，不为证明改造价值制造原版失败。

检查的是回应后的决定：依据是否被使用、未知是否影响正确范围、纠正是否进入下游。出现“根因”“场景”“已理解”等关键词，只能证明这些字出现在输出中。独立判断与实际用户反馈仍有各自边界，合成场景通过不能推定真实用户满意或实际业务收益。
