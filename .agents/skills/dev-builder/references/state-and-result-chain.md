# 存量状态与实际结果链

改变持久值、缓存、内置项、枚举，或实现 UI/异步回写/跨入口行为时读取。先用项目已确认规则决定应发生什么，再用本文定位观察点；无 UI、无持久化或无外部宿主的任务不补造这些环节。

## 删除定义以后，沿读写路径找旧值

从本次变更的对象出发，找创建、加载、编辑、保存、重新打开与展示的实际入口。沿调用方查找引用，不只搜索常量定义；序列化旧值、缓存、导入文件或历史配置可能经过另一条路径回来。

对会改变判断的对象，记录其身份和来源：稳定 ID、类型/来源标记、用户自建还是系统提供，以及哪些数据属于用户。显示名相同不能证明身份相同。用最小脱敏/合成 fixture 保留这些区别，不读取私人数据来凑样本。

再按已有规则分支处理：

- 只禁止新建，旧对象仍需可读：限制真实创建入口，保留规定的旧数据解释。
- 旧对象需转换：确认映射、失败处置、保留数据和授权；用加载与保存路径验证转换，不因发现旧值便默认删除。
- 规则要求隐藏或移除某一来源的内置对象：核对来源条件，保护相似的用户对象及相关历史。
- 不知道旧对象该怎样处理：交主 Agent 原来源、候选解释和具体影响；已确认的新建限制或无关 Task 可继续。

**足够条件**：新对象、代表性旧对象和相近但应保留的对象，经过本次适用的真实入口后满足确认规则；保存后重开仍成立。只检查内存数组或删掉定义不能覆盖持久化承诺。没有实际运行时，把调用链判断与待验项分开交接。

## 把成功响应追到用户真正拿到的结果

选一条真实任务，沿输入 → 临时编辑 → 请求 → 领域处理 → 返回结果 → 实际应用/写回 → 保存/重开追踪。项目没有的环节省略；不能因为某个环节有函数或返回 200 就认为下游已经完成。

遇到异步、跨端或多个编辑者时，在真正决定写入的边界核对：结果属于哪个对象和请求，基于哪次输入，当前编辑是否变化，用户是否完成规则要求的确认。展示成功、收到结果、应用成功、保存成功分别找可观察事实；禁止用成功提示掩盖写回失败。

用能暴露覆盖问题的时序走一次：请求发出后改变当前编辑，再让旧请求返回。依据已确认的冲突规则决定保留候选、拒绝应用或合并；规则未定就回主 Agent，不照搬本文案例的答案。若允许重试或重复回调，再核对它会不会重复写入或覆盖新状态，不能从一次顺序成功推导并发正确。

按需要记录实际前后状态与请求归属，避免只保存聊天中的“已处理”。本地 mock、桥接、服务与目标宿主各说明证明范围；只有实际目标入口完成规定动作，才能声称该入口已验证。

## 验证初态和隔离必须由入口实际消费

测试 fixture 要满足生产路径的前提：合法对象身份、权限、状态和顺序。若为了调用底层函数跳过入口条件，明确该测试只证明底层规则，再用必要的契约/集成检查覆盖真实入口；不能把不可达状态的绿色结果当成功能证明。

会写用户状态的验证，使用项目已有隔离机制及自己创建的临时数据。核对 UI、CLI、后台进程等实际参与入口消费的目录/配置确实一致；通过可安全展示的诊断值或行为对照证明它读取了测试对象。仅创建临时目录或设置一个无人读取的变量不足以证明隔离。隔离未落实时暂停会污染真实数据的执行，继续只读追踪；清理只针对本次创建的资源且沿授权。

## UI 的实现检查接回设计

涉及界面时，沿已有组件与设计决定实际观察变更页面及相关相邻页面：真实内容长度、窄容器、滚动/溢出、加载/错误状态，以及本次受影响的键盘、焦点和危险操作。观察应能说明用户是否看得见、够得着、理解下一步；不要以截图存在或颜色相似代替可完成任务。没有浏览器结果就明确未渲染，不推定主观视觉优劣。

## 交接什么

在已有回执中交代规则来源、实际入口、身份/状态分歧、使用的隔离初态、已观察的前后结果和未走通的边界。若反例推翻原理解，由主 Agent 更新相应 Spec/设计/Task/验收并送达下一角色。需要完整示范时读 [字幕草稿案例](async-proofreading-case.md)，其中业务规则仅在该例定义。
