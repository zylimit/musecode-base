# 原创贯穿例：字幕草稿的异步校对

本例完全虚构，用于演示同一规则怎样被计划、实现、诊断、审查、测试、交付和学习实际消费。不是用户项目事实，不是已运行的测试，不指定技术栈、宿主、目录或框架。其他 Skill 只引用本例，不另写一份业务口径。

## 唯一业务规则

假设编辑员使用本地字幕工具，人工编辑和保存已经可用，这次只增加异步校对候选：

- **C1 对象与版本**：一次校对请求绑定字幕稿 ID、请求 ID、发出时的编辑版本与文本快照；当前编辑与已保存版本分别可辨认。候选只能作用于它所属的稿件。
- **C2 返回不是应用**：服务返回后只登记候选和来源，不自动覆盖当前编辑或保存文件。请求期间人工编辑可以继续；旧请求的候选仍可查看，并说明它基于旧版本。
- **C3 显式应用**：编辑员查看候选后明确选择“应用并保存”。写入前核对他确认时的当前编辑版本；若此后又有编辑则报告冲突，保留当前稿与候选，重新比较后才能产生新的应用决定。写入成功才显示已保存；失败保留可继续工作的当前稿和候选并说明未保存。
- **C4 重复提交**：同一个应用意图重试不得重复生成新版本或再次覆盖后来的编辑。重复结果可查询，不能用一个成功提示替代对实际写入的核对。新的明确选择形成新意图，不把它当旧重试。
- **C5 本地交付**：本次只要求生成本地包，并允许在临时目录解包检验；包须包含查看已有稿件和候选所需资源，离开源码目录也能打开。新校对仍依赖外部服务，未承诺离线生成候选。安装、远端发布、Git 与生产数据操作均未授权。

这些约束只适用于本例。真实项目的冲突、自动保存、重试和离线规则必须读其实际来源，不能把 C1–C5 默认为所有产品要求。

## 一次可重复的时序

| 步骤 | 给定动作/事实 | 依据规则要观察的结果 |
|---|---|---|
| 1 | 稿件 A 已保存 v7“距入口120米”，发出 q1，快照为 v7。 | 请求归属可辨认，保存状态尚无变化。 |
| 2 | 编辑员把当前稿改成 v8“入口向西120米”，尚未手动保存。 | 当前编辑与已保存 v7 可区分。 |
| 3 | q1 返回候选“距入口约120米”。 | 按 C2，当前 v8 仍在；候选明确来自 v7，磁盘仍是原保存状态。服务成功不足以证明此观察。 |
| 4 | 编辑员比较后明确以当前 v8 为依据应用候选；实际写入成功。 | 按 C3 得到一次新保存版本，页面与重开内容相符。这里的取舍由虚构编辑员作出，不由 AI 自动替他丢掉“向西”。 |
| 5 | 因响应丢失重复同一应用意图。 | 按 C4 核对实际版本/内容没有再次变化；不是只断言第二次请求返回成功。 |

另一条对照：在确认与实际应用之间再编辑，按 C3 应冲突且保留新稿；没有再次编辑的正常应用仍应成功。还有“候选属于稿件 B”的拒绝对照，它依据 C1，而不是凭新造的权限默认。

## 阶段消费

**计划**：目标是编辑员拿到可比较、可显式应用的候选。沿结果反推：请求归属与版本契约由谁提供，候选显示/实际写入由谁负责，怎样控制返回顺序、读取保存结果和重开。用现有 Task 绑定实现与证据产生者；共享契约未明不能让前后端各猜一份，已明确部分可先做。mock 返回只能解除本层未知，不能宣布外部服务已连通。

**实现**：从真实用户入口追到处理函数和写入边界。检查 q1 返回走的是登记候选还是应用动作，当前编辑版本是否在真正写入处参与判断。传入版本字段但无人消费，仍不能保护 C3。使用隔离稿件并核对每个参与入口实际读取它；服务响应、候选显示、保存成功和重开分别观察。

**诊断与复验**：若步骤 3 后 v8 消失，先保留该初态与时序。候选解释可以是返回处理器直接替换编辑，或回填时误用了保存状态；比较首次分歧出现在内存更新还是文件加载。控制同一输入与返回顺序，查第一个非预期写入，而不是无因重启。原复现必须能因 C2 被违反而失败；修复后原锁和正常应用都要复验，实际运行后才记录结论。

**审查**：从“应用并保存”这条承诺追按钮、请求、领域判断、实际文件与可见结果。finding 在既有 Evidence 中说明 v7→v8→q1 的最小复验和预期/实际差异；未运行时说明为静态推导。不能用“有版本字段”“测试返回成功”证明 C2/C3，不能只检查功能后漏掉 required trust lens。

**测试**：预期直接取 C1–C4，控制迟到、正常应用、确认后再编辑、重复意图和必要失败路径。可先在状态边界测试，再按实际失效点与 controls 补真实入口/重开；不要求每个断言都完整 E2E。分别核对内存当前稿、磁盘保存状态、候选归属及版本次数，测试结果不由被测写入函数自己计算。

**交付**：依据 C5，实际检查本次包包含入口和资源，再在不依赖源码目录的临时环境打开已有稿与候选；外部服务未实测就保留该边界。只改清单而未重新生成包不能修复缺文件。包验证结束也不能宣称已安装或发布；没有必要为 C5 重新询问已授权的本地准备。

**学习与后续采用**：若 C2 在派单前已明确，AI 却把“服务成功”写成“已完成应用”，这是有依据的行为纠正；若 C2 是用户此刻才提出，先更新项目事实，不能倒算为先前已知。记录事件不能证明已修复。下一位 tester 引用 C2 采用上述时序断言、记录实际观察，才是一个可核对的采用结果；再次阅读同一事件不增加 occurrences，也不因有效教学轮次或沉默评分。

## 可以交接的最小内容

派单引用 C1–C5 中实际适用的条目、当前 Task、有关状态/时序和预期来源，并附明确的未决项。回执区分已写实现、实际跑过的边界、未验证和下一负责者。读过此例或生成了一份计划都不构成行为 PASS；最终结论继续使用真实项目当前主体的独立证据。
