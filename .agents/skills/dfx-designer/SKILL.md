# dfx-designer

- 版本：1.0.0
- 适用：新系统定 DFX 基线、老系统补质量目标、发布前定验收口径。不适用：纯功能需求（走 product-spec-builder）。
- 输入：`docs/REQ-*.md` + 架构方案 + 线上事故史/合规要求。
- 输出：DFX 目标表（入 REQ 或独立 `docs/DFX-*.md`）+ 威胁表/预算表（如适用）。

## 步骤

1. 从损失推导目标：先列"坏了会怎样"（丢单/泄露/停服/错账），再定目标；目标分三档：承诺（必须做到，有验收）、候选（争取，注明条件）、基线（当前实测，不达标先补观测再承诺）。
2. 定测量语义：分清结果定义/目标依据/设计机制/采集实现/验证结果五层，不拿下层替代上层。每个指标写清观察单位（意图≠尝试≠记录）/起止事件/窗口归属/取消超时未知处理/采集盲区；分母必须保留失败（未完成不移出分母，零样本写无样本不是 100%）；成功判据必须可数、技术无关、有基线、有反向指标。
3. 扫 13 维（性能/容量/可用性/可靠性/可观测/安全/隐私/合规/可维护/可扩展/兼容/成本/韧性）：逐维判 critical/high/medium/low + 验收证据；security/safety/privacy 三维永不可豁免。
4. 安全威胁表：按"触发条件→攻击面→后果→缓解→验收"逐条列；隐私走收集/使用/存储/销毁四段 + 数据最小化；性能预算表写死数字（p99/错误率/资源上限）。
5. 缺口进待定表（谁能答/押后到/不答先按什么做），不把猜测写成目标。
6. 交接：DFX 目标是架构的输入（arch-designer 的承接点），也是 test-builder 的验收来源；关键取舍进 `progress.md` Decisions。
7. 高风险发布前用 review 模式复检：逐条核"目标→证据→缺口"链不断。

## 约束与红线

- 无测量语义的目标不得进入承诺档；无验收证据的 DFX 条目视为未完成（`ARCHITECTURE.md` 红线 3）。
- 隐私底线：发布产物绝不含个人数据/密钥/开发者路径，无例外（`docs/QUALITY_CHECKLIST.md` PRI）。
- 合规声称（等保/GDPR/WCAG）须有对应证据，不空喊。

## 验收

- 每条承诺档目标有分子分母口径 + 验收命令/观测位 + 反向指标。
- 威胁表每条有缓解与验收；预算表数字与架构容量评估一致。

## 示例

"下单接口要快" → 追：p99 多少/什么量级下/慢了谁受损 → 定"p99 < 300ms @ 500rps（压测，见 SCALING.md），超时熔断+降级有观测" → 威胁表加"超时重试风暴"条。
